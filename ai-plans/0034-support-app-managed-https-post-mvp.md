# Support app-managed HTTPS (post-MVP)

> Issue: [#34](https://github.com/chA0s-Chris/ShadowDrop/issues/34)

## Rationale

Allow deployments that cannot or do not want to place a reverse proxy in front of ShadowDrop to terminate TLS in Kestrel with an operator-provisioned certificate. Keep the existing plain-HTTP container behavior as the default and continue to recommend a reverse proxy when its certificate automation, request controls, or routing boundary is needed.

## Acceptance Criteria

- [x] Support an optional HTTPS listener through standard ASP.NET Core configuration supplied by environment variables or a configuration file, while retaining plain HTTP on port `19423` as the default when HTTPS is not configured.
- [x] Allow the HTTPS listener to use an operator-provisioned certificate mounted into the container, with no certificate or private-key material committed to the repository or baked into the image.
- [x] Keep certificate passwords and private-key material out of the application's startup logs, verified by a test that starts the host with a password-protected certificate and asserts the captured log output contains neither the password nor the key.
- [x] Fail startup when an HTTPS listener is requested without a usable certificate or private key rather than silently falling back to an insecure endpoint.
- [x] Make the container image advertise optional HTTPS port `19424` without binding it by default and without changing the existing `EXPOSE 19423` behavior or the Compose healthcheck commands.
- [x] Keep the loopback HTTP listener and the existing Compose healthcheck working in the documented app-managed HTTPS example, and document that the bundled health probe uses default certificate trust and cannot validate private or self-signed certificates.
- [x] Add automated tests that complete a real TLS request against the configured Kestrel endpoint, reject invalid or incomplete certificate configuration, and preserve the default HTTP endpoint behavior.
- [x] Document certificate provisioning and renewal responsibilities, read-only Docker volume mounting, secret handling, port publication, and client trust for private or self-signed certificates.
- [x] Update `README.md`, `docs/DEPLOYMENT.md`, and `docs/DEPLOYMENT_HARDENING.md` with an app-managed HTTPS example, the continued reverse-proxy recommendation, and guidance that names the `ShadowDrop__ApiExposure__*` toggles and loopback-only publication of port `19423` as the replacement for the route restrictions a reverse proxy would otherwise enforce.

## Technical Details

Use the endpoint and certificate configuration already loaded by `WebApplication.CreateBuilder` instead of adding certificate fields to `ShadowDropOptions` or loading `X509Certificate2` instances in application code. The documented environment-variable path should combine `ASPNETCORE_HTTPS_PORTS` with the standard `ASPNETCORE_Kestrel__Certificates__Default__Path` and password/key settings; equivalent `HTTPS_PORTS` and `Kestrel:Certificates:Default` values can be supplied by a configuration file. This keeps PFX and PEM/private-key provisioning aligned with Kestrel, lets the framework validate the certificate when the server starts, and leaves `DependencyInjection.ConfigureServices` responsible only for the existing request-body limit. Do not add automatic certificate issuance, ACME renewal, mutual TLS, forced HTTPS redirection, HSTS, or custom TLS protocol selection as part of this issue.

Keep `ASPNETCORE_HTTP_PORTS=19423` in `Dockerfile` so existing deployments and the in-container health probe remain unchanged, and add optional container HTTPS port `19424` to the image metadata. `ShadowDrop.HealthProbe` uses default certificate trust and offers no CA option, so the loopback HTTP listener has to stay bound for the Compose `healthcheck` command to keep working behind a private certificate. The image must not contain a development or production certificate. Deployment examples should mount a certificate directory read-only with permissions readable by the image's non-root user, obtain the password from an environment secret rather than a committed settings file, set the HTTPS port and Kestrel certificate keys, and publish only the HTTPS port when Kestrel is the public edge. Certificate creation, trust distribution, renewal, and safe replacement remain operator responsibilities. Keep both existing Compose files unchanged and provide app-managed HTTPS as a documented
Docker/Compose override snippet in `docs/DEPLOYMENT.md` instead of a new Compose file, so the CI Compose validation list stays at `compose.local.yaml` and `compose.mongodb.yaml`.

Add focused API tests that start a real Kestrel listener on an ephemeral port with a temporary test certificate, call a mapped health endpoint over HTTPS with a client that trusts only that test certificate, and assert the expected response. The existing API tests all run on `TestServer`, so this needs a small TLS host fixture in `ShadowDrop.Api.Tests` that binds `https://127.0.0.1:0` and resolves the assigned port through `IServerAddressesFeature`; the self-signed certificate generation in `tests/ShadowDrop.E2E.Tests/Infrastructure/SelfSignedTlsListener.cs` can be reused for the test certificate. Cover missing files, unusable certificate/private-key combinations, and wrong credentials at startup, plus a regression case showing that the unconfigured application still binds HTTP as before. Because no application code loads certificates, those failure cases assert that host startup fails through Kestrel's own validation rather than through a ShadowDrop-side check. Drive at least one
test through configuration values instead of environment variables so the documented `HTTPS_PORTS` and `Kestrel:Certificates:Default` file shape is covered as well. Keep generated certificate material in temporary test storage and avoid weakening certificate validation globally or relying on the ASP.NET Core development certificate.

In the deployment documentation, distinguish transport encryption from the controls supplied by a reverse proxy. Explain both PFX and PEM/private-key configuration shapes supported by Kestrel, container port and volume examples, password injection, hostname/SAN matching, CLI CA trust options for private roots, and how to keep the HTTP listener private when it remains available for health checks. State that direct Kestrel HTTPS does not provide the route isolation, throttling, or certificate automation described in the hardening guide, so a reverse proxy remains the preferred Internet-facing topology when those controls are required. Where a reverse proxy would otherwise enforce route restrictions, point operators at the `ShadowDrop__ApiExposure__*` toggles and at publishing port `19423` on loopback only, because the health endpoints stay mapped and cannot be filtered without a proxy.
