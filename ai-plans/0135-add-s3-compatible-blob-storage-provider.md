# Add S3-Compatible Blob Storage Provider

> Issue: [#135](https://github.com/chA0s-Chris/ShadowDrop/issues/135)

## Rationale

Allow ShadowDrop deployments to store encrypted blobs in AWS S3 or compatible object stores while keeping blob storage independently selectable from the metadata provider. The implementation must preserve the existing provider-neutral storage contract, stream large transfers with bounded memory, support efficient ranged downloads, and make provider changes explicit because selecting S3 does not migrate existing blobs.

## Acceptance Criteria

- [ ] An `S3` blob provider implements `IBlobStorage` save, open, and idempotent deletion semantics without buffering an entire large object in memory or on local disk.
- [ ] Blob storage remains independently selectable from LiteDB or MongoDB metadata, and the existing filesystem and GridFS combinations continue to work without configuration changes.
- [ ] S3 configuration supports a bucket name, region, optional service endpoint, optional opaque key prefix, optional static credentials, and path-style addressing for compatible services.
- [ ] When static credentials are omitted, the provider uses the standard AWS credential chain so workload, container, instance, profile, and environment credentials remain available.
- [ ] S3 settings are validated only when the S3 provider is selected: the bucket name and region must be nonblank, `AccessKeyId` and `SecretAccessKey` must either both be supplied or both be omitted, and `ServiceEndpoint`, when supplied, must be an absolute HTTP or HTTPS URI; invalid configuration fails clearly.
- [ ] The region is required even when a service endpoint is configured, because it supplies the SigV4 signing region rather than only selecting an AWS endpoint.
- [ ] Startup diagnostics and effective-configuration logging never include access keys, secret keys, or session tokens.
- [ ] When the S3 provider is selected, the effective-configuration log line identifies the bucket, service endpoint, path-style setting, and key prefix in use, and reports whether credentials came from static configuration or the AWS credential chain.
- [ ] Object keys are deterministic from the ShadowDrop file ID and disclose no original filename, share token, credential, or other sensitive metadata.
- [ ] The S3 provider persists `BlobKey` as the file ID's bare `N` representation, matching GridFS, while the filesystem provider retains its existing sharded `<first-two-characters>/<file-id>.blob` format.
- [ ] The configured key prefix is applied only when composing S3 object keys and never when persisting `BlobKey`, and the documentation states that changing the key prefix strands existing blobs in the same way changing the provider does.
- [ ] Missing S3 objects surface through the existing provider-neutral `FileNotFoundException` behavior.
- [ ] `DeleteIfExistsAsync` returns `true` only when the object existed and `false` when it did not, so share cleanup's deleted and already-missing counters stay accurate, and repeated deletion remains safe.
- [ ] Uploads read the request stream once and forward-only without requiring a seekable request stream; payload buffering uses one fixed 8 MiB part buffer per upload, plus completion metadata bounded by S3's 10,000-part limit and ordinary AWS SDK overhead.
- [ ] Content that reaches the end of the stream before the first part buffer fills is stored with a single non-multipart request; larger content uses multipart transfer.
- [ ] When S3 is selected, configuration fails clearly if `Upload:MaxBytes` exceeds the maximum object size supported by the fixed 8 MiB part size and S3's 10,000-part limit.
- [ ] Zero-length and sub-part-size objects round-trip correctly through save, open, and delete.
- [ ] Uploads propagate cancellation and make a best-effort attempt to abort incomplete multipart uploads after failure or cancellation.
- [ ] `OpenReadAsync` returns a seekable provider stream that translates reads after a seek into S3 byte-range requests instead of downloading or discarding bytes from the beginning of the object.
- [ ] ShadowDrop does not create or mutate the configured bucket at application startup.
- [ ] When the S3 provider is selected, the readiness endpoint reports unready while the configured bucket is unreachable, misconfigured, or inaccessible; the check is read-only, does not create or mutate the bucket, and requires no permissions beyond the documented least-privilege policy.
- [ ] Deployment documentation covers AWS S3 and RustFS provider configuration, TLS, service endpoints, and path-style addressing, and extends the persistence-provider combination table with the `LiteDb`/`S3` and `MongoDb`/`S3` rows and their required configuration values.
- [ ] Deployment documentation includes a least-privilege AWS policy covering `s3:ListBucket`, `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:AbortMultipartUpload`, and any other permissions required by the chosen upload operations, and explains that `s3:ListBucket` is required for reliable missing-object detection.
- [ ] Deployment documentation covers the multipart part size and its per-upload memory cost, lifecycle cleanup for abandoned multipart uploads, coordinated backup/restore, and the absence of automatic blob migration.
- [ ] Automated unit, provider-contract, and integration tests cover configuration, opaque key generation, streaming save/open, ranged seeking, deletion, missing objects, cancellation, multipart cleanup, and representative LiteDB/S3 and MongoDB/S3 combinations.
- [ ] S3 integration tests use a version-pinned RustFS container image rather than MinIO or LocalStack, declared alongside the existing pinned test images; Renovate configuration validation and a dry run confirm that the custom manager detects the committed pin and excludes preview and glibc tag families, and update selection is verified with a temporary known-older plain-beta fixture when the committed pin is already current.
- [ ] S3 integration tests provision their own test bucket outside application startup and do not require live AWS credentials.

## Technical Details

Add `S3` to `BlobStorageProvider` and extend `StorageOptions` with a nested `S3` sub-object bound from `ShadowDrop:Storage:S3`, holding `BucketName`, `Region`, `ServiceEndpoint`, `KeyPrefix`, `UsePathStyle`, `AccessKeyId`, and `SecretAccessKey`. The default `appsettings.json` gains only non-secret placeholder structure; credential values are never committed and are supplied through environment variables or a secret store. Update `ShadowDropOptionsBinding`, the default configuration, dependency injection, and effective-configuration logging so only the selected provider's settings are required and SDK credential material is never included in logs. When S3 is selected, require a nonblank bucket name and region, require static credentials as a complete access-key/secret-key pair or not at all, and accept a service endpoint only when it is an absolute HTTP or HTTPS URI. The region stays mandatory even alongside a service endpoint because it supplies the SigV4 signing region; it is not an
alternative to the endpoint. Extend the effective-configuration log line so an S3 deployment reports its bucket, service endpoint, path-style setting, and key prefix, plus whether credentials were resolved statically or through the SDK credential chain, while continuing to omit the credential values themselves. Preserve `ShadowDropOptions.RequiresMongo` as a function of the metadata and GridFS selections so either metadata provider can be paired with S3. Register the S3 implementation only when storage-backed API features are enabled, following the existing lifetime and provider-selection pattern.

Implement `S3BlobStorage` with the official AWS SDK for .NET while keeping AWS request, response, client, and exception types inside the S3 storage implementation and closely related internal helpers. Take the S3 client as an injected dependency rather than constructing it inline, so tests can substitute a recording fake without a container. Build a deterministic object key from the file ID, optionally rooted beneath a normalized configured prefix, and do not derive keys from user-supplied names or tokens. Treat a missing, empty, or whitespace-only `KeyPrefix` as no prefix. Otherwise trim surrounding whitespace and leading or trailing `/` characters, reject a value that becomes empty through normalization, and preserve all internal characters and repeated separators unchanged. Compose the object key as `<normalized-prefix>/<file-id:N>`, or `<file-id:N>` when there is no prefix. The `BlobKey` carried in `UploadBlobDescriptor` and persisted to metadata stays the file ID's bare `N`
representation for S3, matching `MongoGridFsBlobStorage`; `LocalBlobStorage` retains its existing sharded relative-path key format. The prefix is applied only when composing the object key for an S3 request. `KeyPrefix` is part of a deployment's durable identity: changing it once uploads exist strands the previously written objects under the old prefix, exactly as switching providers does. Always configure the client with the supplied region — for AWS it selects the endpoint, and for compatible services it supplies the signing region — and when a service endpoint is configured, apply it together with the path-style option so the endpoint overrides endpoint resolution while the region continues to drive signing. Construct explicit credentials only when a complete static credential set is configured; otherwise let the SDK resolve its standard credential chain. The application should verify configuration shape but must neither create nor mutate buckets during startup.

Stream uploads through one fixed-size reusable payload buffer per upload so payload memory is bounded independently of the upload length and non-seekable request streams are supported. Fill that buffer before choosing a transfer strategy: if the stream reaches its end before the buffer fills, store the buffered content with a single `PutObject`, which needs one round trip, no upload ID, and no cleanup obligation, and which makes zero-length objects work by construction; only when the buffer fills without reaching the end does the provider start a multipart upload and send the buffered content as its first part. Fix the part size at 8 MiB as a constant rather than an operator-tunable setting: it sits comfortably above S3's 5 MiB minimum for non-final parts, and at the 10,000-part limit it leaves roughly 80 GB of object headroom, far above the current `Upload:MaxBytes` default of 4 GiB. When S3 is selected, reject `Upload:MaxBytes` values greater than `8 MiB * 10,000` during
configuration validation with a clear error, and cover that boundary with an automated configuration test so the server never accepts an upload size that can exhaust S3 part numbers. Payload-buffer memory is the part size multiplied by the number
of concurrent uploads; each upload also retains part numbers and ETags bounded by the 10,000-part limit plus ordinary AWS SDK overhead, so state that relationship in the deployment documentation. Complete the multipart upload only after all parts succeed. Track the upload ID and, on any exception or cancellation, attempt `AbortMultipartUpload` with a cleanup token that is not already cancelled, log cleanup failure without exposing credentials, and rethrow the original failure; the single-request path has no such obligation because a failed `PutObject` leaves nothing behind. Return the exact uploaded byte count through `UploadBlobDescriptor`.

Implement an internal read-only seekable stream backed by ranged `GetObject` requests. Obtain object length when opening, translate the stream's logical position into `Range` headers, reuse the active response stream for sequential reads, and dispose/reopen it after non-sequential seeks. Bound any read-ahead buffer, honor cancellation, validate seek bounds consistently with the existing download contract, and map S3 not-found responses to `FileNotFoundException`. Deletion must preserve `IBlobStorage`'s existing boolean and idempotent behavior. Because S3 reports success for `DeleteObject` whether or not the key existed, precede the delete with a metadata request so the method returns `true` only for objects that were actually present; `ShareCleanupService` depends on that distinction to separate its deleted and already-missing counters. Require `s3:ListBucket` on the configured bucket in addition to object read permission because AWS S3 otherwise reports a missing object to
`HeadObject` or `GetObject` as `403 Forbidden` rather than `404 Not Found`, preventing reliable provider-neutral missing-object behavior. Any race between the existence check and the delete remains harmless because the desired final state is absence.

Extend readiness so blob-storage health is reported independently of metadata health. Today `IReadinessCheck` is selected solely from the Mongo requirement, which would leave a LiteDB/S3 deployment reporting ready while its bucket is unreachable. Compose the checks instead: retain the existing Mongo ping when metadata or GridFS requires MongoDB, and add an S3 readiness check that issues a `ListObjectsV2` request with a zero key limit against the configured bucket. That request is read-only, creates and mutates nothing, and needs no permission beyond the `s3:ListBucket` grant the provider already requires. Bound it with the same short timeout the Mongo check uses and treat any failure as unready.

Extract the existing blob-storage contract assertions from `MongoPersistenceIntegrationTests` into a reusable provider contract, extend them with the additional required cases, and run the shared contract against filesystem, GridFS, and S3. Within the #135 PR, make the behavior-neutral provider-contract extraction the first commit and keep it green against filesystem and GridFS before adding the S3 implementation in subsequent commits; adding the S3 provider then registers one more implementation against an already-proven contract, which keeps moved assertions distinguishable from changed ones during review. Retain the surrounding behavior coverage in `UploadPersistenceServiceTests`, `ShareCleanupServiceTests`, and `MongoPersistenceIntegrationTests`, and keep focused provider-specific unit coverage for configuration and range-stream behavior outside the shared contract. Prove range behavior at unit level against a fake S3 client that records each `GetObjectRequest.ByteRange`,
asserting that a seek followed by a
read issues a new request starting at the expected offset and that sequential reads reuse the open response stream instead of re-requesting; a container-backed test cannot observe request shape and must not be relied on for that claim. Add a generic Testcontainers fixture around a version-pinned `rustfs/rustfs` image in single-node mode, and run the RustFS suite in the default `Test` target alongside the existing Mongo container tests rather than behind an opt-in category. RustFS is selected because it is a focused, Apache-2.0 S3-compatible server with a small single-node deployment surface; Garage's AGPL licensing and LocalStack's broader emulation and commercial-use licensing make them unsuitable defaults for this suite. This is a deliberate deviation from issue #135, which named MinIO or LocalStack, and MinIO's own licensing posture argues against it as a default test dependency. A live-AWS smoke test is out of scope for this plan; the RustFS suite is the only S3 integration
coverage required, and if such a test is added later it must be environment-gated so the default `Test` target never depends on AWS credentials.

Because RustFS is pre-1.0 and publishes several tag families — plain `1.0.0-beta.N` releases alongside `-preview.N` and `-glibc` variants — registering the pin with Renovate needs more than the current manager shape. Declare the image constant alongside the existing pinned test images following the `MongoDbTestImages.cs` convention, and extend the Renovate custom manager's `managerFilePatterns` and `matchStrings` to cover it: today that manager matches only `MongoDbTestImages.cs` and a hardcoded `mongo:` prefix, so the regex must generalize to capture the image name and tag rather than assuming one repository. State `versioning` explicitly in the renovate comment alongside `datasource`, `depName`, and `packageName`, and add a `packageRules` entry constraining `allowedVersions` to the plain beta family so `-preview` and `-glibc` tags are never proposed; revisit that constraint once RustFS publishes a stable release. Verify the result rather than assuming it: record the exact
configuration-validation and dry-run commands used, confirm that the custom manager detects the committed pin, and confirm that preview and glibc variants are excluded. If the committed pin is already current, use a temporary known-older plain-beta fixture to prove that Renovate selects a newer allowed beta, then restore the fixture before completing the work. A manager that matches nothing fails silently. Isolate the container setup behind test infrastructure, wait for readiness, provision the bucket with test-only administration code, and keep assertions limited to portable S3 behavior. Exercise upload failures and cancellation with non-seekable streams, verify no multipart uploads remain, confirm that seeking returns the same bytes as the equivalent slice, and run representative metadata/blob combinations without turning the integration suite into an end-to-end-heavy test diamond.

Update central package management and the API/test project references for the AWS SDK and test infrastructure. Extend `docs/DEPLOYMENT.md` and relevant README configuration examples with AWS and RustFS examples, safe secret injection, TLS expectations, path-style endpoint setup, lifecycle cleanup as a defense against process termination, provider-selection/scaling constraints, and coordinated backup/restore guidance. Extend the persistence-provider combination table with `LiteDb`/`S3` and `MongoDb`/`S3` rows so the table stays exhaustive; it currently enumerates every supported pairing, and an omission would read as though S3 cannot be paired with LiteDB. Note `us-east-1` as the conventional placeholder region for compatible services that ignore it but still require a signing region. Include a least-privilege AWS policy that grants `s3:ListBucket` on the configured bucket and `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:AbortMultipartUpload`, plus any additional permissions
required by the chosen upload operations, on the configured object prefix; explain that `s3:ListBucket` enables reliable missing-object detection rather than exposing bucket contents to application behavior. State prominently that changing `Storage:Provider` only redirects future lookups and writes; it does not copy or reconcile blobs from the previous provider. The same caveat applies to `Storage:S3:KeyPrefix`, which strands existing objects under the old prefix once it changes.
