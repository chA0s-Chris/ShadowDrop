# Delete share metadata once cleanup succeeds, and hide expired shares at the repository boundary

> Issue: [#176](https://github.com/chA0s-Chris/ShadowDrop/issues/176)

## Rationale

Cleanup deletes ciphertext but keeps metadata forever, so a share that expired years ago still holds its original filenames, plaintext lengths, plaintext hashes, KDF salts, and owner credential ID on disk, and the store grows without bound for the lifetime of the deployment. That contradicts the redaction posture the administrative surfaces are built around. Make expiry the point where a share stops being visible to ordinary lookups, and make a successful cleanup run delete the metadata outright instead of marking it complete, so the only shares that survive a run are the ones whose blobs could not be deleted — which stay visible to operators precisely because they need attention.

## Acceptance Criteria

- [x] Resolve shares by token hash through a repository lookup that never returns an expired or revoked share, so the download path cannot observe one regardless of its own checks.
- [x] Keep the by-identifier share lookup privileged and unfiltered, so the visibility rule applies only to token-hash resolution and administrative reads are unaffected.
- [x] Keep cleanup able to reach expired and revoked shares through an explicit privileged query.
- [x] Keep single-use file enforcement rejecting files referenced by an expired or revoked share that has not been purged yet.
- [x] Acquire a durable cleanup operation claim covering every file identifier of a share before starting any blob deletion for it.
- [x] Delete or confirm absent every blob of a claimed share without deleting any uploaded-file metadata row during that blob phase.
- [x] When cleanup-claim acquisition conflicts, perform no destructive work; after acquisition, retain every metadata row and the cleanup claim when any blob deletion or retained-blob accounting operation fails, record `cleanup-failed`, and retry the invisible share on the next run.
- [x] Treat uploaded-file metadata that is already absent during cleanup as success for that file, so a retried share converges on deletion.
- [x] Only after every blob has been deleted or confirmed absent, delete the uploaded-file metadata rows and then the share record; keep a share whose metadata deletion failed partway as a `cleanup-failed` candidate that converges on a later run.
- [x] Remove `ShareCleanupState.Completed`, `ShareListStatuses.CleanupCompleted` including its `CanonicalOrder` entry, and `ShareListCleanupStates.Completed`, so every listed share reports exactly one of `cleanup-pending` or `cleanup-failed`.
- [x] Remove the now-unreachable `upload-metadata-missing` failure category and its `CanonicalOrder` entry.
- [x] Remove the cleanup-completed share count from the status counts, the administrative server status contract, its service mapping, the startup summary log, and the CLI status output.
- [x] Reject `cleanup-completed` as an unknown value in the API status filter, the CLI `--status` option, and share-list cursor validation.
- [x] Read shares already persisted with the removed completed state back as `cleanup-pending` and purge them in the first cleanup run after the upgrade, without a migration step.
- [x] Keep `share list` and the operational status counts reporting active, expired, revoked, cleanup-pending, and cleanup-failed shares until their records are deleted.
- [x] Keep the cleanup-run guard non-blocking so overlapping cleanup runs report `Skipped`, while making durable operation claims rather than the guard's lease responsible for data safety.
- [x] Before reading uploaded-file metadata or inserting a share, atomically acquire one durable share-creation operation claim covering every requested file identifier; make share-creation and cleanup claims mutually exclusive for each file across API instances.
- [x] Associate every operation claim with its proposed share identifier and a durable lifecycle so abandoned pre-insert claims can be conditionally aborted, while indeterminate insertions are resolved or retried idempotently with the same share identifier without exposing any file to cleanup in between.
- [x] Retain a cleanup claim through blob-deletion failures and metadata-deletion retries so an external deletion that outlives a cleanup-run lease cannot race with a new share.
- [x] Update Chaos.Mongo to 0.7.0, extend the MongoDB cleanup-run lease for the complete run through `IMongoLock.TryExtendAsync()`, and stop starting new cleanup work when extension returns `false` or no successful extension occurs before the owned lease expires.
- [x] Provide equivalent visibility, deletion, retry, cleanup-claim, and coordination behavior for the LiteDB and MongoDB metadata providers.
- [x] Add automated tests.
- [x] Update `README.md`, `docs/API.md`, `docs/CLI.md`, `docs/DEPLOYMENT.md`, and `docs/SECURITY_TRADEOFFS.md` for the removed values and metadata being deleted rather than retained after cleanup.

## Technical Details

The work splits into three rules. Visibility flips at expiry, which is time-based and deterministic. Deletion happens on the cleanup run, which is schedule-based. The states that become unreachable are removed rather than retained as reserved values. Nothing about the externally observable behavior may depend on when cron last fired.

Enforce visibility inside `IShareMetadataRepository` rather than in each caller, so the property holds for callers that have not been written yet. `GetByShareTokenHashAsync` needs the current time — either as a parameter or through an injected `TimeProvider` — and returns `null` for a share that is expired or revoked. `DownloadFileService.cs:599` is the only production caller of that lookup, and its existing expiry branch becomes unreachable defence in depth rather than the primary check; `DownloadLookupStatus.ExpiredShare` can go with it, since it and `InvalidShare` already map to the same `401` in `DownloadEndpoints`. The by-identifier `GetAsync` stays privileged and unfiltered so administrative reads — including the share inspection planned in #172 — keep seeing a share until its record is deleted. `GetCleanupCandidatesAsync` stays privileged too, as does the `IsFileReferenced` scan inside `CreateAsync`: if that scan stopped seeing expired shares, a file belonging to an
expired-but-unpurged share could be re-shared while its ciphertext is still on disk.

Cleanup-run exclusion and data-mutation exclusion serve different purposes. Keep `IShareCleanupCoordinator` as the dedicated non-blocking scheduling guard used only to make overlapping cleanup runs report `Skipped`. Put data safety in a new durable operation-claim repository shared by `CreateShareService` and `ShareCleanupService`. A claim records its kind, operation identifier, proposed or existing share identifier, and complete set of file identifiers. In MongoDB, store the complete set in one claim document and enforce a unique multikey index over its file identifiers, so acquiring a multi-file operation is one atomic insert even on standalone servers. The LiteDB implementation performs the equivalent check and insert in one database transaction. Reacquiring an existing claim with the same kind and operation identifier is idempotent; any claim owned by another operation is a conflict.

`CreateShareService.CreateAsync` generates the share and operation identifiers before reading any uploaded-file record, acquires one share-creation claim covering the full request, and keeps it until the share insert succeeds or definitively fails. Model creation claims with a conditional lifecycle: an acquired claim can be aborted only by first winning a state transition that prevents its owner from proceeding, while the complete proposed share record is persisted before atomically entering the committing state and issuing the insert. An indeterminate insertion is resolved by querying or retrying that same share identifier and payload, never by expiring the claim based only on elapsed time. Reconcile unfinished operations through the claim repository so a process failure before insertion cannot block the files forever. Once the share is known to exist, its existing unique file index supplies the permanent single-use guarantee and the temporary operation claim can be removed. Cleanup
acquires the mutually exclusive cleanup claim for all files of its candidate share before touching blob storage and retains it until every uploaded-file row is gone. A delayed external deletion is therefore fenced by durable state even after a cleanup-run lease is lost, and no metadata-mutation lease is needed.

Chaos.Mongo 0.7.0 exposes `IMongoLock.TryExtendAsync(TimeSpan?, CancellationToken)` for extending an owned, unexpired lock, so update its version in `Directory.Packages.props` and use that API throughout the MongoDB cleanup run. A `false` result is definitive ownership loss and makes the lock invalid; an exception leaves the lock state untouched, so the coordinator may retry only while `IsValid` and `ValidUntilUtc` leave enough headroom, and must signal loss if no extension succeeds before expiry. Extension must not resurrect an expired lease, and release remains conditioned on the holder token. `MongoShareCleanupCoordinator` exposes ownership loss through its lease handle so `ShareCleanupRunner` and `ShareCleanupService` stop starting new shares or files. Already claimed work remains safe and converges on a later run. Keep `InProcessShareCleanupCoordinator` non-blocking and unchanged in purpose. Short, injectable lease and extension intervals make extension, transient errors, and
loss deterministic in integration tests.

Replace the `Completed` branch of `TryRecordCleanupAttemptAsync` with deletion. `ShareCleanupService` already tracks per-file outcomes, so a share qualifies for metadata deletion exactly when every file either had its blob deleted or was already absent, retained-blob accounting succeeded, and no failure category was recorded. Deletion needs a new bounded operation on `IShareMetadataRepository` and a per-file delete on `IUploadedFileMetadataRepository`; the new operation-claim repository needs acquire, resolve, and release operations. Implement these for both LiteDB and MongoDB, following the existing default-throwing interface member convention used by `GetListProjectionsAsync` and `TryMarkBlobDeletedAsync`. A provider-level transaction spanning claims, uploads, and shares is not an option: two of the three MongoDB integration fixtures run standalone servers, which have no multi-document transactions.

Make cleanup explicitly two-phase per share. If cleanup-claim acquisition conflicts, perform no blob work and record the share as `cleanup-failed`. After acquisition, the blob phase deletes or confirms absent every reachable blob and reconciles retained-blob accounting, but deletes no uploaded-file row. A blob or accounting failure retains every row and the cleanup claim and records `cleanup-failed`. Only when the complete blob phase succeeds does the metadata phase delete uploaded-file rows, then release the cleanup claim, and finally delete the share record. The share record stays last because it is what keeps partial work reachable as a cleanup candidate; a failure before that final delete records `cleanup-failed` and retries. If uploaded-file deletion fails partway, the retained claim blocks share creation, and the next run treats already-absent rows as success before continuing. `TryCleanupFileAsync` must likewise treat metadata that was already absent when the run began as
success rather than the `upload-metadata-missing` failure it records today at `ShareCleanupService.cs:146`. That classification cannot survive in any form, because the blob key lives inside the uploaded-file record: once the row is gone there is nothing left to probe the blob with, so "already deleted" and "orphaned" are indistinguishable. `ShareCleanupService.cs:146` is its only producer, which makes `ShareCleanupFailureCategories.UploadMetadataMissing` a third unreachable wire value to remove alongside the completed states.

Removing the completed states cascades through `ShareLifecycle`: the `Matches` filter arm, the `Statuses` switch, and the `CleanupState` mapper each lose their `Completed` branch, after which `Statuses` always appends exactly one of `cleanup-pending` or `cleanup-failed`. It also reaches surfaces beyond listing — `ShareStatusCounts.CleanupCompleted` flows through `OperationalStatusService.cs:104` into the administrative server status contract, through `CompositionRoot/Startup.cs:91` into the startup summary, and out as the CLI's `shares-cleanup-completed:` line. Remove the count from every consumer and its tests, along with the legacy five-argument `ShareStatusCounts` constructor whose parameter order differs from the primary one. `ShareCleanupState` is persisted as an uppercase string rather than an ordinal — `LiteDbShareMetadataRepository.cs:271` uses `nameof(ShareCleanupState.Completed).ToUpperInvariant()` — so confirm the MongoDB representation matches before touching the remaining
members' numbering. Dropping the value from
`ShareListStatuses.CanonicalOrder` narrows the API status filter, the CLI `--status` validation in `ShareListCommandHandler`, and `ShareListCursor.IsCanonicalStatusSet`, which invalidates any previously issued cursor encoding it. Narrowing both the listing values and the status count is acceptable because the commits introducing them reached `main` but were never released. Records already carrying the removed state need no migration: both providers parse an unrecognized value back to `ShareCleanupState.Pending` (`LiteDbShareMetadataRepository.cs:97,126`, `MongoShareMetadataRepository.cs:87,108`), so a previously completed share becomes a cleanup candidate again, finds its blobs already absent, and purges itself on the first run after the upgrade. That run therefore clears the whole historical backlog at once, which is intended rather than incidental.

Administrative visibility is deliberately unchanged: `share list` and the status counts keep seeing every share until its record is deleted. A permanently failing blob deletion must stay diagnosable, otherwise unbounded visible metadata is merely traded for unbounded invisible metadata plus orphaned ciphertext and no operator signal.

For tests, the existing `ShareCleanupServiceTests` assertions that a successful run leaves `CleanupState == Completed` invert into assertions that the share record and its uploaded-file rows are gone, and the LiteDB repository tests and MongoDB integration fixture need matching coverage for token-hash invisibility, privileged cleanup and by-identifier lookups, two-phase deletion, and retry convergence. Prove that a later blob failure leaves every upload row intact, while a metadata deletion failure after all blobs succeed leaves the share visible as `cleanup-failed` and converges on retry. Exercise atomic multi-file claim acquisition, idempotent reacquisition by the same operation, conflicts with another operation, recovery after abandonment before insertion, definitive share-insert failure, and both possible indeterminate insertion outcomes. Add deterministic concurrency coverage for LiteDB and for two API instances sharing MongoDB: pause blob deletion after the durable cleanup claim
is persisted, delay it beyond the cleanup-run lease interval, and prove that concurrent share creation cannot acquire the file even after lease ownership is lost. Verify separately that an overlapping cleanup reports `Skipped` while the run guard remains valid. With short injected MongoDB lease intervals, prove extension across a long run, retry after a transient extension exception, definitive loss after a `false` result or lease expiry, and that loss stops new cleanup work before another instance enters. Share-listing tests covering `cleanup-completed` are removed rather than rewritten, and startup-summary tests lose `CleanupCompletedShares`. Blob-provider behavior stays covered by the existing `IBlobStorage` contract tests rather than being re-proven per provider here.

The documentation pass is not only additive: `docs/DEPLOYMENT.md:174` states that successful cleanup reconciles records to `deleted`, and `:180` that completed cleanup reports zero retained bytes without erasing the share's file count. Both describe behavior this change removes, because the share and its file rows no longer survive the run at all.

Reclaiming completed uploads that no share references — including completion timestamps, grace-period policy, bounded candidate scheduling, and orphan-specific failure reporting — is deliberately deferred to follow-up issue #177. Retention policy beyond expired and revoked shares, the upload-credential lifecycle, the cleanup schedule and its trigger endpoint, and the administrative listing and inspection contracts beyond the removed values all remain out of scope. Issue #172 stays blocked until this lands.
