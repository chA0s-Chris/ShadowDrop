# Reclaim unreferenced completed uploads

> Issue: [#177](https://github.com/chA0s-Chris/ShadowDrop/issues/177)

## Rationale

Completed uploads that are never referenced by a share currently retain both their metadata and ciphertext forever, because cleanup only walks shares. Reclaim those uploads after a generous grace period without deleting active reservations, recently completed files, or files referenced by any share. This is a follow-up to #176 and lands after it so the sweep can reuse its durable cleanup-claim state and metadata-mutation coordination.

## Acceptance Criteria

- [ ] Record a completion timestamp for every completed upload.
- [ ] When a legacy completed upload has no completion timestamp, stamp its completion timestamp with the current time when first encountered and wait a full grace period from that stamp before making it eligible.
- [ ] Delete an unreferenced completed upload when its completion timestamp is at or before the configurable grace-period cutoff, defaulting the grace period to seven days, and delete or confirm its blob absent before deleting its metadata.
- [ ] Never sweep an upload reservation, whether claimed or unclaimed, a completed upload younger than the grace period, or a file referenced by any share, including an expired or revoked share awaiting purge.
- [ ] Durably claim an eligible upload for cleanup before starting blob deletion so share creation cannot adopt it, including when an external deletion outlives a distributed lease.
- [ ] Reconcile abandoned acquired and committing share-creation claims before retrying a conflicting sweep claim, while performing no destructive work when the conflict remains unresolved.
- [ ] Retain the cleanup claim and metadata for retry when blob deletion or retained-blob accounting fails, and retry idempotently when metadata deletion fails after the blob is gone.
- [ ] Recover and release an orphaned sweep claim when a crash occurs after upload metadata deletion but before claim release, inspecting at most 50 sweep claims per run separately from the candidate budget and rotating inspected claims so retained ones cannot hide later orphans.
- [ ] Count sweep deletion failures in the cleanup result, report the run as a partial failure, and log only the affected file identifier.
- [ ] Report sweep counters for candidates inspected, uploads deleted, blobs already missing, and failures, and surface them in the administrative cleanup response and the CLI `share-cleanup` output.
- [ ] Inspect at most 200 upload candidates per run.
- [ ] Prioritize never-inspected and then least-recently-inspected candidates, using completion time and file identifier as deterministic tie-breakers so referenced or failing records cannot starve the backlog.
- [ ] Add provider indexes that bound candidate-selection work for LiteDB and MongoDB.
- [ ] Provide equivalent behavior for the LiteDB and MongoDB metadata providers.
- [ ] Add automated coverage for grace-period boundaries, legacy timestamps, reservation states, referenced uploads, cleanup claims, deletion failures, retry convergence, batching, and starvation prevention.
- [ ] Update operator, deployment, API, CLI, and security documentation for the new retention setting and cleanup behavior.

## Technical Details

Extend uploaded-file persistence with two timestamps: a completion time and a last-sweep-attempt time. `TryCompleteReservationAsync` stamps the completion time in both `LiteDbUploadedFileMetadataRepository` and `MongoUploadedFileMetadataRepository` when a reservation transitions to completed. The timestamps are provider-internal scheduling state, so prefer keeping them on the provider documents rather than widening `UploadedFileRecord`, which flows through download and share paths that have no use for them. A legacy completed document without a completion time is not eligible; the sweep stamps it with the current time on first encounter, so it waits a full grace period from that stamp.

Add the retention setting to `CleanupOptions` as a `TimeSpan` (`UnreferencedUploadRetention`, default seven days) bound from `ShadowDrop:Cleanup:UnreferencedUploadRetention` in `d.hh:mm:ss` form, and validate it in `ShadowDropOptionsBinding` alongside the existing cron validation; it must be positive, reported with the same key-named error style the cron validation uses. The sweep gets no separate on/off switch: cleanup itself has none either, and a second configuration state would double the paths to test. An operator who does not want reclamation configures a retention long enough that nothing becomes eligible, which the documentation states explicitly.

Run the upload sweep inside the same cleanup run as share cleanup, after the share phase, under the same cleanup-run lease and lease-validity callback — `ShareCleanupRunner.RunWithLeaseAsync` is the natural seam. Prefer a dedicated sweep service (e.g. `UploadSweepService`) that the runner invokes after `ShareCleanupService.RunAsync`: it keeps the share service single-purpose, makes the result merge explicit, and gives the sweep its own test surface. Running second lets the share phase converge partially failed purges first and gives the candidate query the freshest state, but ordering carries no correctness weight: safety against a file losing or gaining a share reference mid-run rests entirely on the durable claim and the post-claim reference re-check described below, never on scan ordering.

Candidate selection is a bounded query on the uploaded-file repository: completed (not reserved, claimed or unclaimed) and either missing a completion timestamp or carrying one at or before the grace-period cutoff (`completion <= now - retention`), ordered by never-inspected first, then least-recently-inspected, with completion time and file identifier as deterministic tie-breakers, limited to 200. Legacy records with a null completion timestamp must be included by the query, or they would never surface: they sort as never-inspected, count against the 200 budget, are stamped with the current time on inspection, and become eligible only a full grace period after that stamp. Both providers need an index that bounds this query including the null-timestamp shape — LiteDB via `EnsureIndex` on the sweep-ordering fields, MongoDB via a compound index created where the collection's other indexes are declared. Stamp the last-sweep-attempt time on every inspected candidate, including ones
skipped as referenced or failing, so they
rotate to the back of the queue and cannot starve the backlog.

Per candidate, the sweep first acquires a durable claim for the single file through `IShareOperationClaimRepository.TryAcquireAsync`. The existing claim contract is share-scoped, so extend it minimally: add a new `ShareOperationClaimKind.SweepUpload` and pass the sweep's operation identifier as the `ShareId`, since no share exists — a non-null convention, nothing more. The unique multikey index over claim file identifiers already makes any two claims on the same file mutually exclusive regardless of kind, and share-creation reconciliation (`GetUnfinishedShareCreationsAsync`, `TryBeginCommitAsync`) continues to filter on `Kind == CreateShare`, so sweep claims never enter it. Derive the sweep operation identifier deterministically from the file identifier so a later run can reacquire a retained claim idempotently while its upload metadata remains discoverable, mirroring how #176 converges retried cleanup claims.

A claim conflict is not automatically a live share creation: it can be an abandoned `CreateShare` claim. Extract the reconciliation currently private to `CreateShareService` into a shared collaborator used by both share creation and the sweep. For a conflicting file, conditionally abort an `Acquired` creation claim; for a `Committing` claim, retry its persisted proposed-share insertion and release it once insertion succeeds or definitively fails. After successful reconciliation, retry sweep-claim acquisition once. If the conflict remains unresolved, skip the candidate without destructive work or a deletion-failure count; a later run can reconcile it. This preserves the existing conditional lifecycle rather than inventing time-based claim expiry.

Only after the sweep claim is persisted does the sweep re-check share references through a new privileged per-file lookup on `IShareMetadataRepository`; the reference scan inside each provider's `CreateAsync` single-use enforcement shows the shape, and the check must see expired and revoked shares awaiting purge. Declare the member with a default-throwing implementation, as `TryDeleteAsync` already does, so the interface's existing test doubles keep compiling. A referenced file releases its claim and is skipped. The order matters: the durable claim fences share creation before the reference check, closing the race where a share adopts the file between check and deletion, and the claim — not the cleanup-run lease — is what keeps an external blob deletion that outlives the lease safe, exactly as in #176.

Deletion is three-phase per file, mirroring the share cleanup contract: delete or confirm absent the blob, then record the retained-blob accounting transition via `TryMarkBlobDeletedAsync`, and only then delete the metadata row via `TryDeleteAsync` and release the claim. A blob-deletion or accounting-transition failure retains the claim and the metadata row, counts a failure, and retries on a later run; the accounting step is what keeps administrative storage totals from counting ciphertext that is already gone when a later phase fails. A metadata-deletion failure after the blob is gone retries idempotently, treating an already-absent row as success so the record converges on deletion.

Deterministic reacquisition alone cannot recover a crash after metadata deletion but before claim release, because the deleted upload no longer appears in the candidate query. Add a starvation-safe recovery query for `SweepUpload` claims limited to 50 claims per run, backed by claim-kind and recovery-ordering state/indexes in both providers. Orphaned claims arise only from a crash in a narrow window, so a smaller budget than the candidate scan keeps a healthy run cheap while still draining a backlog over a few runs. For each recovery claim, look up the upload metadata: release the claim when the row is absent, because the deletion protocol only removes that row after the blob is deleted or confirmed absent; leave a claim with a present row to the normal candidate scheduler. Rotate inspected recovery claims so retained claims cannot permanently hide later orphaned ones. This recovery batch is separate from, and does not weaken, the limit of 200 uploaded-file candidates per run.

Extend `ShareCleanupResult` with sweep counters (candidates inspected, uploads deleted, blobs already missing, failures) and include sweep failures in the `Failures` total the runner uses, so `CleanupRunStatus` records a partial failure when only the sweep failed. The already-missing counter mirrors the existing `BlobsAlreadyMissing` split rather than folding both outcomes into deletions: records written before #176 can already carry a deleted retention state, so the first sweep after an upgrade would otherwise report freed storage it never freed. `ShareCleanupResult` is the administrative cleanup response body and the CLI mirrors it field-for-field, so the new counters flow through `ShareCleanupResultContract` and the `share-cleanup:` output line, keeping response and CLI output aligned. Log failures with the file identifier only — no blob key, file name, or other metadata, consistent with the redaction posture.

Retention policy for uploads still referenced by shares and all credential-lifecycle behavior stay out of scope.

Tests cover the boundary cases named in the acceptance criteria for both providers: grace-period boundaries (just under, exactly at, and just over the cutoff), legacy documents stamped on first encounter, claimed and unclaimed reservations never selected, referenced files skipped with their claims released — including references from expired and revoked shares — ordinary claim conflicts with concurrent share creation, reconciliation of abandoned `Acquired` and `Committing` creation claims, idempotent reacquisition of a retained sweep claim while upload metadata remains, bounded and starvation-safe recovery after a simulated crash between successful metadata deletion and claim release, blob-deletion and accounting-transition failures retaining claim and metadata, retry convergence after metadata-deletion failure, the 200-candidate and 50-claim batch limits, and rotation of inspected candidates so a permanently failing record cannot starve fresh ones. Documentation updates cover the new
`ShadowDrop:Cleanup:UnreferencedUploadRetention` setting — including that a long retention is the way to effectively disable reclamation — the new sweep counters, and the sweep behavior in `README.md`, `docs/API.md`, `docs/CLI.md`, `docs/DEPLOYMENT.md`, and `docs/SECURITY_TRADEOFFS.md`.
