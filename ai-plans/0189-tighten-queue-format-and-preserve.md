# Tighten queue format and preserve relative upload paths

> Issue: [#189](https://github.com/chA0s-Chris/ShadowDrop/issues/189)

## Rationale

Make a download queue describe exactly one share, remove redundant per-file data, and preserve the uploader's portable relative directory layout by default when `upload --queue-out` creates the queue, while retaining an explicit flat-output mode for inputs collected from unrelated locations. Introduce the tighter contract as a clean queue format version 2 break while ShadowDrop is pre-1.0 and queue files remain short-lived.

The `--flatten` option is a deliberate addition beyond issue #189, which asks only for an input-root option and for escaping files to be rejected. Preserving relative paths by default turns previously accepted uploads of scattered inputs into hard failures, so the flat mode is the intentional escape hatch for that case rather than unplanned scope.

## Acceptance Criteria

- [x] Queue format version 2 stores required `serverUrl` and `shareToken` values at the queue root, keeps optional embedded credentials queue-scoped, and removes the repeated share values from file entries.
- [x] Version 2 file entries require `fileId`, `fileName`, and `length`, retain optional `plaintextSha256`, and treat an omitted `outputPath` as `fileName`.
- [x] Queue serialization writes only the canonical version 2 shape and omits `outputPath` when it equals `fileName`.
- [x] Version 1 and other unsupported queue versions are rejected by shared queue validation with a `queueVersion` error that tells the user to recreate the queue; no legacy reader or migration path is introduced.
- [x] Version 2 queue validation requires `/` for directory separators in explicit `outputPath` values and rejects `\` in every effective output path; a `fileName` containing separators is valid only when a safe explicit `outputPath` is present.
- [x] Queue validation rejects unsafe effective output paths, including empty segments, traversal, absolute, drive-qualified, and UNC paths, and rejects both duplicate and ancestor/descendant file-directory conflicts at case-insensitive path-segment boundaries.
- [x] Queue downloads resolve one share and retrieve one manifest per queue while preserving per-file selection, progress, resume, integrity verification, failure reporting, and output-root containment.
- [x] `upload --queue-out` preserves paths relative to the command's initial working directory by default and supports `--input-root <directory>` for files under another root; a relative input-root value is resolved against the captured initial working directory.
- [x] In default preserve mode, a selected file outside the effective input root fails before any upload or share-creation request with an error naming the offending file and pointing to `--input-root` or `--flatten`.
- [x] `upload --queue-out --flatten` discards source directories and produces a flat, collision-safe set of queue destinations from the display-name override when present and the manifest-selected file name otherwise.
- [x] `--input-root` and `--flatten` each require `--queue-out`, are mutually exclusive, and `--flatten` permits inputs from unrelated locations because no source root is derived or validated.
- [x] All deterministic queue destinations are computed and validated from the selected files and normalized display names before any upload or share-creation request, including root containment, portable segment sanitization, duplicate detection, and ancestor/descendant conflict detection.
- [x] Recipient-facing display-name overrides replace the destination leaf while preserving its derived relative directory in the default mode and remain the flat destination leaf in `--flatten` mode.
- [x] Interactive uploads preserve `--input-root` and `--flatten` when delegating to the shared upload workflow and generate the same queue destinations as equivalent non-interactive uploads.
- [x] `queue create` continues to generate flat, collision-safe destinations from manifest data, and uploads without `--queue-out` retain their existing filename and manifest behavior.
- [x] Automated tests cover versioned parsing and Native AOT serialization, single-share enforcement, optional and nested output paths, portable path validation, input-root and flatten option handling, renames and collisions in both path modes, existing-share queue creation, and nested queue downloads.
- [x] CLI and security documentation describe the version 2 queue format, the intentional breaking change and queue-recreation guidance, relative-path, input-root, and `--flatten` behavior, and embedded-credential sensitivity.

## Technical Details

Move `ServerUrl` and `ShareToken` from `QueueFileEntry` to `QueueFile`, make `QueueFileEntry.OutputPath` optional, and update `FormatConstants`, the source-generated `QueueJsonSerializerContext`, and `QueueFileParser` around the version 2 wire contract. `FormatConstants.QueueVersion` becomes `"2.0"`; `FormatConstants.ShadowDropVersion` stays `"1.0"`, so the marker version is unaffected by the queue format break. Keep the parser and serializer limited to the current model: version 1 and unknown versions must fail explicitly with queue-recreation guidance, without legacy DTOs, normalization, or migration logic. That guidance belongs in `QueueFileParser.Validate` as the `queueVersion` validation message rather than in a CLI special case, because it is a property of the format break rather than of one command; every caller of the shared parser then surfaces it through the existing `{path}: {message}` rendering.

Centralize effective-output-path resolution as `OutputPath ?? FileName`. Validate portable relative path syntax independently of the host operating system, require `/` in explicit nested `OutputPath` values, and reject `\` in effective paths rather than interpreting it differently by host. When `OutputPath` is omitted, apply the same path validation to `FileName`; a server-announced name containing separators therefore needs a safe explicit `OutputPath`. Reject not only case-insensitive duplicate effective paths but also segment-boundary prefix conflicts such as `docs` and `docs/report.txt`, then retain the final full-path containment check under the selected download output root.

Rework `DownloadCommandHandler.ExecuteQueueAsync` around one validated queue-level `ShareReference` and one shared manifest retrieval. If manifest loading stays lazy so the progress reporter can preserve per-file outcomes, share the same task/result across entries rather than issuing one request per file. Continue matching each queue entry against manifest filename, length, and optional digest before downloading.

Add an `--input-root <directory>` value and a `--flatten` Boolean option to `CliApplication` and `UploadCommandOptions`, both scoped to queue-producing uploads. Validate the option contract before file I/O or network work: each option requires `--queue-out`, and they must not be combined. Capture the command's initial working directory once so later path resolution is not affected by mutable process state, and resolve a relative `--input-root` against that captured directory. Update `InteractiveUploadCommandHandler` to carry both values when it reconstructs `UploadCommandOptions`, so interactive and non-interactive uploads share the same validation and queue generation behavior.

Introduce a focused queue destination resolver with explicit preserve and flatten modes. Preserve mode resolves and validates each selected `FileInfo` against the explicit input root or captured working directory. Normalize the root and every selected file identically with `Path.GetFullPath` and do not resolve symbolic links, so containment stays predictable and unit-testable without touching the filesystem; applying the same normalization to both sides keeps a symlinked working directory or a platform alias such as macOS `/tmp` from making an in-root file look like an escape. The resolver operates on path segments, reuses or extends the existing portable filename rules for every segment, rejects root escapes, and serializes retained separators as `/`. Flatten mode skips source-root derivation entirely, accepts files selected from unrelated or external directories, and uses only each manifest-selected leaf. Both modes must compare canonical path segments with
`StringComparer.OrdinalIgnoreCase`, resolve exact destination collisions with the existing deterministic suffixing behavior, and reject file/directory hierarchy conflicts where one effective path is an ancestor of another.

Run the destination resolver against all selected files and locally normalized display-name overrides before invoking `UploadCommandExecutor`, so every root, sanitization, duplicate, and hierarchy failure that can be known from command input occurs before remote side effects. Preserve the resulting destination plan through the upload rather than recomputing it from mutable process state.

After successful uploads, associate each prepared destination with its `UploadFileExecutionResult.UploadedFileId` and pass that mapping into `QueueFileBuilder`. The builder should verify the prepared leaf against the manifest-selected `fileName`, including any display-name override, and treat an unexpected mismatch as a remote consistency failure rather than silently recomputing the destination after share creation. `QueueCreateCommandHandler` continues to build flat destinations from manifest entries without source hints. The builder should set `OutputPath` only when the prepared or manifest-derived portable destination differs from `FileName`, preserving the serializer's compact canonical form.

Document the version 2 contract in `docs/CLI.md` under the existing "Download queues (multi-file, resumable)" section, which currently describes queue usage but never the wire format: add a "Queue file format (version 2)" subsection carrying the canonical JSON shape, the field list, and the breaking-change and queue-recreation guidance, alongside the `--input-root` and `--flatten` behavior in the `upload` reference. Extend the embedded-credential sensitivity note in `docs/SECURITY_TRADEOFFS.md` to the queue-scoped credentials object. Leave the "Queue File Format" section in `PROJECT_CONCEPT.md` untouched: it records the original concept shape (with a root-level `target` and `shareId` that shipped ShadowDrop never used) and is referenced as a historical artifact, so `docs/CLI.md` becomes the single normative home for the format.

Update shared parser tests, CLI builder and command-handler tests, interactive upload tests, and the real queue download scenario in proportion to each seam. Include Windows and POSIX path forms regardless of the test host, rejection of version 1 and unknown versions, backslash rejection, case-only duplicates and ancestor/descendant conflicts, renamed nested files, relative and absolute input roots, deterministic preflight failures before any HTTP request, unrelated external inputs accepted by `--flatten`, invalid option combinations, interactive option propagation, and directory creation during download. Keep all JSON paths source-generated so CLI Native AOT publication remains supported.

Deliver this as one atomic queue-contract change built in three independently reviewable stages: first the version 2 model, parser, serializer, and downloader rework; then the `--input-root` and `--flatten` options with the destination resolver, its preflight validation, and the real-process E2E coverage required to verify that layer independently; then documentation and final acceptance-criteria completion. Stage one is self-contained and reviewable on its own, because the queue format break and the single-share download path do not depend on upload-side path preservation.
