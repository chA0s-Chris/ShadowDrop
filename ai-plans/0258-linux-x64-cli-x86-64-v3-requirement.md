# Linux x64 CLI 0.9.1 requires an x86-64-v3 CPU

> Issue: [#258](https://github.com/chA0s-Chris/ShadowDrop/issues/258)

## Rationale

The glibc `linux-x64` CLI release binary of 0.9.1 refuses to start on x86-64-v2 CPUs (`CPU ISA level is lower than required`), whereas 0.9.0 ran there. The cause is the build environment, not this repository or .NET: `publish-cli-linux` runs on `ubuntu-latest`, which is now Ubuntu 26.04 and installs packages from the `amd64v3` archive variant. Its `libc6-dev` ships a `crt1.o` carrying an `x86 ISA needed: x86-64-baseline, x86-64-v2, x86-64-v3` ELF note, the linker copies that note into the AOT binary, and glibc's loader enforces it. The amd64 CLI Docker image is affected too, because `StageCliDockerArtifactsCore` stages the same artifact as `/usr/local/bin/shadowdrop`.

The goal is to build the glibc Linux CLI (`linux-x64`, `linux-arm64`) in Microsoft's pinned NativeAOT cross-build containers, whose Ubuntu 18.04 sysroot carries no ISA markers, and to make `PublishCliArtifacts` fail loudly whenever an x64 Linux binary needs more than `x86-64-baseline`, so this cannot regress silently on any host.

## Technical Details

**Workflow shape (`.github/workflows/release-artifacts.yml`).**
- Mirror `publish-cli-linux-musl`: a `strategy.matrix.include` with `runtime` (`linux-x64`, `linux-arm64`), `target` (`PublishCliLinuxX64`, `PublishCliLinuxArm64`) and `image`; `runs-on: ubuntu-latest` for both, since both cross images run on an x86_64 host and arm64 is a cross build. Keep the job id `publish-cli-linux` so `collect-release-artifacts`'s `needs` stays valid.
- Put the image reference in the matrix (`image: mcr.microsoft.com/dotnet-buildtools/prereqs:<tag>@sha256:<digest>`) rather than embedding it in the `run:` script. This deviates slightly from the issue's wording ("digests inside `run:`") but meets its intent and its Renovate requirement (a `# renovate:` comment next to each digest), and keeps the regex trivial and independent of shell quoting. Pass `${{ matrix.image }}` as a `docker run` argument and the release version through `env`, as the musl job does.
- The digest must be resolved at implementation time (`docker buildx imagetools inspect <image:tag>`). At planning time both tags resolved to single-platform manifests: `cross-amd64` `sha256:3d9b12839eb1352678e577c3fada879ea1e92fe5923da4d260786e7b6d7b0075` and `cross-arm64` `sha256:15c15aac729f136bc69c32bdb2582324a226f19bcabf24cb4d283b1bacbc2ff9`; re-resolve rather than trusting these values, and tag + digest must both appear (`tag@sha256:…`), so Renovate and humans can read the intent.
- The container has no .NET SDK and no `git` guarantee. `build.sh` installs the SDK from `global.json` when no `dotnet` is on `PATH`, which needs `curl`, `bash` and `perl` (its `FirstJsonValue` helper); the Nuke `GitRepository` attribute needs `git` and, because the checkout is owned by a different uid than the container user, `git config --global --add safe.directory /workspace`, exactly like the musl job. Verify during the local `docker run` that the image provides these; if `git` or another tool is missing, install it with the image's package manager inside the container script (a container-internal install of a non-compiler tool is acceptable; only host-runner `apt-get`/toolchain installs are banned, and the compiler/sysroot must stay untouched). Side effect that stays: the SDK now follows `global.json` (10.0.403 plus `rollForward: latestFeature`, which only matters when a `dotnet` is already on `PATH`) instead of floating to the newest 10.0.x.
- Upload `artifacts/publish/cli/*/shadowdrop-*-${{ matrix.runtime }}` as `shadowdrop-cli-${{ matrix.runtime }}`, with `if-no-files-found: error`. `collect-release-artifacts` copies every `shadowdrop-*` file regardless of artifact name, so it needs no logic change; `release.yml` restores `linux-x64`/`linux-arm64` artifacts from the bundled `cli/` directory by file name, so it is unaffected. The old artifact name `shadowdrop-cli-linux` has no other consumer (verified by search).
- Files written by the container are root-owned in the workspace; upload and later steps only read them, as for the musl job.

**Build pipeline (`build/BuildPipeline.Publish.cs`).**
- New targets are intentionally parallel to the musl ones (`DependsOn(Restore)`, `.After(Clean, RestoreTools)`) with one-element RID arrays. Add `LinuxX64CliRuntimeIdentifiers` / `LinuxArm64CliRuntimeIdentifiers` next to the existing arrays, and let `LinuxCliRuntimeIdentifiers` stay the union used by `PublishCli` and `PublishCliLinux`.
- Cross-sysroot activation is auto-detected by directory existence, not by a build parameter: local runs without `/crossrootfs` are unaffected and the ISA guard catches a silent fallback to a tainted host toolchain. Detection only applies to the two glibc RIDs; musl builds run in Alpine and must not pick up a sysroot. The `ObjCopyName` choice becomes: sysroot directory present for a glibc RID -> `SysRoot` + `LinkerFlavor=lld` + `ObjCopyName=llvm-objcopy`; otherwise `linux-arm64` keeps `ObjCopyName=aarch64-linux-gnu-objcopy` exactly as today (the SDK has no usable fallback for a cross-arch objcopy name, so it must stay explicit), and every other RID sets nothing. This keeps the issue's promise that local `PublishCli`/`PublishCliLinux` runs are unaffected; no new parameter. The `StageCliDockerArtifacts` comment then says release builds use the cross image and the host cross-toolchain (`gcc-aarch64-linux-gnu`) is a local fallback only. Focused verification of the fallback is inspection of the resulting `DotNetPublish` settings (the sysroot-less branch is the pre-change code path, unchanged); no local arm64 cross-toolchain publish is required.
- ISA guard: put the logic in a new, Nuke-independent file `build/ElfIsaGuard.cs` (illustrative contract: an `internal static class ElfIsaGuard` with `IReadOnlyList<String> ParseNeededLevels(String readelfOutput)` that returns the trimmed, comma-separated tokens of the `x86 ISA needed:` line, ignoring `x86 ISA used:`, and `void Verify(String artifactPath, Func<String, String, String?> readNotes)` where `readNotes(tool, artifactPath)` returns the `-n` output or `null` when the tool executable does not exist). `Verify` tries `llvm-readelf`, then `readelf`, throws naming both tools if both return `null`, and throws naming the artifact and the levels other than `x86-64-baseline` otherwise. The Nuke project compiles it (it globs `build/*.cs`); `BuildPipeline.Publish.cs` supplies the production `readNotes` over the existing `RunProcess` helper (missing executable -> `null` via the `Win32Exception` thrown by `Process.Start`; a non-zero exit code throws, never silently passes). Run it on the published executable in the intermediate directory, before `File.Copy`, so a failing build leaves no versioned artifact that Docker staging could pick up. Runs on every Linux x64 publish, not only release builds (decision from the issue). The musl container build already contains `binutils` through `build-base`, so the musl x64 leg keeps working; confirm this during implementation rather than assuming it.
- Fail-closed on a missing tool is a deliberate choice: a guard that silently skips would defeat its purpose, and typical Linux dev hosts and both release images have `readelf` or `llvm-readelf`. Hosts without binutils must install it to publish x64 Linux artifacts. Mention this next to the guard.
- Automated tests (required by `ai-plans/AGENTS.md`): add a small test project `tests/ShadowDrop.Build.Tests` (new; the existing test projects reference `src/` only and the Nuke project is not built by the solution) that includes `..\..\build\ElfIsaGuard.cs` via `<Compile Include=... Link=...>` rather than referencing the Nuke project, and add it to `ShadowDrop.slnx`. It follows `tests/AGENTS.md` (NUnit, FluentAssertions, hand-written test doubles, top-level test class, data-driven cases); the `readNotes` delegate is the test double seam for readelf output, tool-missing and tool-preference cases, with sample outputs modelled on the real `readelf -n` text for 0.9.0 (baseline only) and 0.9.1 (baseline, v2, v3). The `Test` target already globs `tests/**/*.Tests.csproj`, so no pipeline change is needed. This is a unit test (no external I/O). Beyond these, the one-time real-asset check is the end-to-end evidence: download the 0.9.1 release asset and run the actual `ElfIsaGuard` code against it, via a temporary scratch harness that must not be committed (if `readelf` is not on the host, run it inside the cross image with `docker run`), plus the local container build above.

**Compatibility and constraints.**
- glibc floor is out of scope: the new binaries need GLIBC_2.16 (x64) / 2.17 (arm64), lower than 0.9.1's 2.34, and this issue neither enforces nor documents a minimum.
- No Docker-specific change: `Dockerfile.cli` copies the staged `linux-x64` artifact, so the image is fixed once the artifact is. `release.yml` stages the artifact restored from the release bundle; no guard is added there.
- Historical plans (`ai-plans/0069…`, `0162…`, `0163…`) still describe the host toolchain and stay unchanged.
- Planning-time probes: the cross image tags exist and resolve to digests (above); local host has no `readelf`, which is why the guard check may need the container. No full test suite is needed or relevant for this change; apply the scoped checks listed in the criteria.
